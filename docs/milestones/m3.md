# M3 – Communication

Source: instructions from the project owner, saved verbatim (Step 1 scope, Phases A–E and the review checklist). The client brief is in `docs/client-brief.md`.

## STEP 1 — Build M3: enquiries, requirements, chat, quotations, notifications, moderation

Scope:
1. Enquiries: the "Chat / Enquire" button on the product page now works. Each enquiry opens a conversation tied to that listing. A buyer (or another seller) can also contact a seller from their portfolio page (general conversation). Sellers can never enquire about their own listings.
2. Offers: in a listing conversation the buyer can send a structured offer (amount + currency + note). The seller can accept, decline, or counter. No payments.
3. Buyer requirements: buyers post a requirement (gemstone type, category, shape, carat range, budget range + currency, certificate needed, origin preference, quantity, deadline, notes). Approved sellers in matching categories get notified and can respond. Each response starts a requirement-based conversation. Buyers can close or edit requirements. Add a public-to-sellers "Requirements board" in the seller dashboard with filters.
4. Quotations: sellers send a quotation inside a conversation (listing or custom item, price, currency, quantity, validity date, terms). Statuses: SENT, ACCEPTED, DECLINED, EXPIRED, WITHDRAWN. Downloadable quotation PDF.
5. Chat: in-platform conversations with text and image/PDF attachments (via StorageProvider, same validation). Read receipts, unread counts, conversation list with search. Use polling or server-sent events; no separate websocket server. Users can block or report a conversation.
6. Contact-detail moderation: detect and mask phone numbers, emails, URLs, and WhatsApp/Telegram/Instagram handles in messages, offers, quotations and requirement notes. Include obfuscated forms (spaced digits, "at"/"dot", number words). Flagged messages go to an admin queue. Repeat offenders get a warning, then a temporary messaging restriction.
7. Notifications: in-app bell with notification centre plus email via the EmailProvider, for new enquiry, new message (batched, not one email per message), offer/quotation events, requirement matches and responses. Users set their notification preferences.
8. Dashboards: buyer Enquiries and Conversations tabs work (sellers see these too for their buyer activity). Seller dashboard gets an Inbox, Requirements board, Quotations and Offers pages.
9. Admin: flagged-message queue, reported conversations, requirements moderation, and authorised conversation viewing. Every admin view of a private conversation needs a reason and is audit logged.
10. Rate limits on messages, enquiries, requirement posts and reports.
11. Demo seed: add demo conversations, a few requirements, offers and quotations, all labelled "Demo".

Multiple subagents, same pattern as before:

- All schema changes + migration (conversations, participants, messages, attachments, offers, requirements, requirement responses, quotations, notifications, preferences, moderation flags, blocks/reports).

Only you edit schema/migrations.

Phase B — parallel subagents, each in its own git worktree with file ownership lists:
1. Buyer agent: enquiry from product and portfolio pages, offers UI, requirement posting/editing/closing, buyer dashboard Enquiries and Conversations tabs.
2. Seller agent: seller inbox, requirements board and responses, quotation create/send/withdraw + PDF, offer accept/decline/counter.
3. Notifications & admin agent: notification bell and centre, email templates (Resend + console), preferences page, admin flagged queue, reports, requirements moderation, audited conversation viewing, demo seed additions, MSG91 + Resend provider implementations.
Each agent uses Phase A services, writes tests, and reports back instead of changing schema or shared helpers.

Phase C — you: merge, resolve conflicts, then run full typecheck, lint, tests and build.
